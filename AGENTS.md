# SERVINCOM Odoo/OCA Repository Instructions

These instructions apply to all work in this repository.

## Repository Identity

- Repository: `SERVINCOM/external_module`.
- Branch/version: `16.0`.
- Target platform: Odoo 16 Community.
- Repository type: public SERVINCOM addon repository.
- Use this repository only for generic, reusable, publishable modules.
- Do not add client-specific logic, secrets, private credentials, database dumps, filestore data, `.env` files, tokens, or real customer data.

## Default Rules

- Follow OCA conventions first.
- Do not modify Odoo core. Use Python inheritance, XML inherited views, `inherit_id`, `xpath`, hooks, or clean extensions.
- Before creating or changing a module, identify Odoo version, target module, dependencies, business workflow, security impact, and update path.
- Keep one concern per module.
- Use lowercase `snake_case` technical module names.
- Prefer Odoo ORM APIs, recordsets, computed fields, constraints, domains, access rules, and Odoo services over raw SQL.
- Avoid unnecessary dependencies. Use Odoo Community and OCA modules only when they provide clear value.
- Never include Python cache files or folders: `__pycache__/`, `*.pyc`, `*.pyo`, or other generated bytecode files.
- Do not reorganize addons into nested category folders unless `addons_path` is reviewed and updated accordingly.

## Required Module Shape

Every new or touched SERVINCOM module should preserve or include:

- `__manifest__.py`
- `__init__.py`
- `models/`
- `views/`
- `security/ir.model.access.csv` when there are new models
- `data/` when needed
- `demo/` when useful
- `i18n/es.po`
- `static/description/icon.png`
- `README.md` or OCA-style `readme/` fragments, following the existing module pattern
- `tests/` when logic, permissions, constraints, integrations, or critical workflows are touched

## Manifest Requirements

Manifest metadata must be explicit:

- `name`
- `summary`
- `version` using OCA-style versioning, for example `16.0.1.0.0`
- `license`
- `author`
- `website`
- `category`
- `depends`
- `data`
- `demo`
- `assets` when needed
- `installable`
- `application`

Default values:

- `author`: `SERVINCOM SOLUCIONES, S.L.`
- `website`: `https://www.servincom.com`
- `license`: `AGPL-3` unless the existing module/repository requires another license

## Language And Translations

- Use English for technical names: models, fields, methods, files, XML IDs.
- User-visible text must be Spanish from Spain through `i18n/es.po`.
- If fields, menus, actions, views, buttons, errors, constraints, wizards, reports, templates, or notifications are added or changed, update `i18n/es.po`.
- Avoid invalid PO occurrences for Odoo 16, especially unsupported manifest-summary occurrences.

## Odoo 16 POS Rules

- Inspect the existing POS component/template before changing POS JavaScript.
- Prefer small component extensions over broad overrides.
- Do not break core POS flows: product screen, payment screen, payment button, customer selector, order list, return/back buttons, session opening, or session closing.
- Declare POS JavaScript/XML assets under `point_of_sale.assets` in the manifest.
- In Odoo 16 OWL/POS JavaScript, avoid `owl.hooks`; use Odoo 16-compatible imports/patterns such as `const { useState } = owl;` when using legacy `odoo.define`.
- If the change touches POS loaders, preserve core loader fields and append only the needed custom fields.

## Git Workflow

- Before finishing, check repository state when available:
  - `git status`
  - `git diff`
  - `git diff --staged` when files are staged
- Do not commit, push, merge, rebase, force push, or perform destructive Git operations unless the user explicitly asks.
- Do not use `git add .` indiscriminately. Stage only files related to the requested change.
- Keep commits small and specific if the user asks for a commit.

## Validation

Before delivery, review:

- manifest dependencies
- Python imports
- XML IDs
- inherited views and `xpath`
- security access and record rules
- Odoo 16 compatibility
- `i18n/es.po`
- `static/description/icon.png`
- module update risks

When practical, run the available checks:

- syntax checks for touched Python/XML
- repository pre-commit if configured
- Odoo update/install on a test database
- module tests if present

Do not hide skipped or failing checks. Report what was run and what remains.

## Odoo 16 Update Command

When suggesting a server update, adapt the database and module name:

```bash
systemctl stop odoo16
su - odoo -c "/opt/odoo16/16.0/odoo/odoo-bin -d <database> -u <module_name> --config /opt/odoo16/config/odoo16.conf --stop-after-init"
systemctl start odoo16
systemctl status odoo16 --no-pager
```

For production databases, require backup/snapshot confirmation before risky changes.

## Final Response Contract

At the end of a task, report:

- affected module
- files created or modified
- whether commit/push was done
- recommended Odoo update command
- minimum functional tests
- risks before testing on a real database
- checks that could not be run
